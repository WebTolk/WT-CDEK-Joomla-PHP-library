# Повторный аудит полей WT CDEK 1.4.0-dev

Статус: **changes required; дальнейшая работа остановлена оператором до продолжения**. Аудит завершён, исправления не выполнялись. Четыре замечания P2 и одно ограничение P3. P0/P1 в проверенном объёме не обнаружены. Этот отчёт уточняет прежний положительный verdict приёмки: ранее пройденные 39 E2E остаются фактом, но не покрывают описанные здесь сценарии.

Scope: все классы `src/Fields`, сервис Deliverypoints, три JS-ассета, тарифный layout, WebAssetItem, registry, новый com_ajax handler, контракты Joomla Form и публичного Tariffinfo. Рабочее дерево с незакоммиченными изменениями; audit не изменял продукт, Git index, ZIP, установленную Joomla или настройки CDEK.

## F1 — P2: retry сбрасывает сохранённый пункт без смены адреса

**Evidence:** `lib_webtolk_wtcdek/media/js/wtcdek-watchfield.js:47` считает `initial` по числу попыток; при ошибке `:90` устанавливает key=null. Новый scan запускает повторную попытку. `wtcdek-deliverypoints.js:37` очищает select при любом loading с initial=false; `:49` также перестаёт сохранять отсутствующий код. В Chrome первый запрос завершился ошибкой, затем `Joomla.Watchfield.scan()` повторил его: адрес `Old address` остался прежним, выбранное `SAVED` стало пустым. Пользователь адрес не менял.

**Impact:** временная ошибка сети и последующее joomla:updated могут потерять сохранённый пункт и заблокировать сохранение required-поля. Аналогичная очистка возможна при повторном связывании элементов адреса с прежним значением.

**Recommended action:** отделить изменение адреса от номера попытки. Сбрасывать выбор на invalidation действительно изменившихся адресных значений; retry не должен менять сохранённый выбор. Проверить также сохранение кода после первой неудачной загрузки и повторного scan.

**Blocked or Not:** блокирует полную приёмку сохранения выбранного пункта.

## F2 — P2: программное изменение Deliverypoints не обновляет зависимые поля

**Evidence:** `wtcdek-deliverypoints.js:26` / `:54` меняют native select и значение; `:24` отправляет только `wtcdek:options-updated`. Общий Watchfield подписан на input/change (`wtcdek-watchfield.js:147`). В Chrome B наблюдает за пунктом A: до изменения адреса A=KNOWN и snapshot B=KNOWN; после invalidation A пустой, snapshot B по-прежнему KNOWN.

**Impact:** цепочка зависимостей расходится с фактическими значениями формы. Зависимые карточки или собственный AJAX-провайдер могут использовать старый код пункта, включая данные для другого адреса.

**Recommended action:** общий контракт должен уведомлять registry о программной смене значения. Отправлять change при фактическом изменении или предоставить явный метод invalidation источника. Предусмотреть дедупликацию и защиту от циклических зависимостей. Проверить цепь город → ПВЗ → зависимый потребитель.

**Blocked or Not:** блокирует приёмку общего обработчика для цепочек полей.

## F3 — P2 / BC: старые layout overrides Tariffinfo дают пустую карточку

**Evidence:** публичный layout в HEAD/1.3.2 выводил `data-watch-field` и `data-tariffs`. Новый scanner (`wtcdek-watchfield.js:157`) ищет только `[data-watchfield]`; необходимые атрибуты теперь выводит строка `layouts/fields/tariffinfo.php:20`. Старое переопределение их не знает. В Chrome сохранена прежняя разметка с data-watch-field/data-tariffs: render-target остаётся пустым, JS-исключений нет.

**Impact:** базовый layout и прежний XML работают, но копия старого layout в шаблоне сайта прекращает отображение данных после обновления. В предыдущих release notes миграция уже отмечена; это всё равно граница обратной совместимости, которую нельзя смешивать с утверждением о полной совместимости minor-версии.

**Recommended action:** добавить совместимый переход для прежней разметки либо явно ограничить гарантию совместимости и оформить миграцию. Для выпуска minor предпочтителен адаптер. Требуется regression test сохранённого публичного layout, а не только обновлённого стандартного.

**Blocked or Not:** блокирует заявление о полной совместимости со старыми layout overrides; на стенде таких overrides ранее не было.

## F4 — P2: validate="options" несовместим с динамическими списками

**Evidence:** `DeliverypointsField.php:46` возвращает только пустой вариант и сохранённый код; AJAX-варианты доступны только браузеру. Native Joomla OptionsRule использует серверные `$field->options`. Probe на Joomla 4.4.14, 5.4.7 и 6.1.3: provider содержит NEW; PHP options=["", "SAVED"]; `validate('NEW')` возвращает JLIB_FORM_VALIDATE_FIELD_INVALID, а `validate('SAVED')` проходит, хотя SAVED отсутствует у провайдера.

У `TarifflistField` обнаружено то же ограничение: OptionsRule не извлекает динамические группы `getGroups()`, и код 136 не проходит. Это **прежняя проблема публичного поля**, его исходник в новой версии не менялся.

**Impact:** форма с обычным `validate="options"` отвергает выбранный пользователем корректный вариант. Без этого правила поле проверяет required, а принадлежность к актуальному каталогу должна подтверждаться отдельно на сервере. Этот результат не означает, что любые формы без options автоматически небезопасны: окончательный контракт принадлежит обработчику сохранения.

**Recommended action:** определить серверный validation contract: правило для Deliverypoints с адресом/фильтрами и проверкой кода, для Tarifflist — проверка по каталогу тарифов. Уточнить поддержку стандартного options и политику временно недоступного API. Не считать сохранённое значение доказательством принадлежности к списку.

**Blocked or Not:** блокирует использование validate="options"; формы без этого правила не затронуты данным отказом. Требует проверки реального сохранения, а не только обновления UI.

## F5 — P3: существующий target не поддерживает повторную конфигурацию/refresh данных

**Evidence:** конфигурация и names читаются только внутри `if (!state)` (`wtcdek-watchfield.js:159`). Key учитывает только values (`:44`). Замена data-watchfield-options у того же DOM-элемента с providerA на providerB и scan оставляет A; даже последующее изменение источника всё ещё использует A. Обновление Joomla Script Options при прежних значениях и joomla:updated тоже не выдаёт новые данные.

**Impact:** при частичном обновлении страницы с сохранением того же контейнера нельзя применить новые параметры/набор данных существующего поля. Замена контейнера новым работает. Это ограничение lifecycle, а не отказ обычного сценария статического XML; обязательная поддержка reconfigure пока явно не согласована.

**Recommended action:** явно определить различие scan/refresh/reconfigure; либо добавить обновление конфигурации и принудительное чтение новых Script Options с отменой старого запроса, либо документировать неизменяемость существующего экземпляра и обязательную замену target.

**Blocked or Not:** не блокирует текущую работу статического XML; требует явного контракта для универсального обработчика.

## Что подтверждено

XML city/zip/fias_guid по наличию отключают watchfield; фильтры нормализуются, строка false сохраняется в Entity; UUID ФИАС не заменён city_uuid; новый handler проверяет POST/token до клиента, скрывает provider exception. WebAsset с Text::script и отдельные renderers корректно подключаются в ранее проверенных native формах. Origin check/path guards/textContent обеспечивают проверенные ограничения в JS. Выборки и фильтры сервиса покрыты offline fixtures.

Новые probes использовали настоящий Chrome DOM и неизменённые JS продукта, но подставной fetch; обращения к CDEK не выполнялись. PHP probes используют настоящие core-классы Joomla и существующий offline bootstrap с запрещённой БД/stub CDEK. Это дополнительные адресные reproductions, не повторная native-install приёмка сайта.

Архитектурное направление общего scanner/provider и отдельных renderers сохранено. Найденные проблемы относятся к state/lifecycle, серверной валидации и BC, не требуют возврата к индивидуальным inline-скриптам.

Дополнение по документации: getAllTariffs() получает каталог от CDEK `/calculator/alltariffs` и кэширует его. Фразу «локальный каталог» в описании поля следует уточнить; custom data source сейчас также сопровождается подготовкой стандартного каталога в PHP.
